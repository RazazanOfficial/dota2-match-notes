# بازیابی اطلاعات ناقص Replay

این سند جریان جاری بازیابی metadata را شرح می‌دهد. اشاره به migration `0023`
در پایین، مربوط به استقرار اولیهٔ این قابلیت است؛ برای انتشارهای بعدی
[راهنمای VPS](deployment-ubuntu.md) را ببینید.

اگر دریافت سادهٔ مچ قبل از آماده‌شدن Replay انجام شود، `dota_matches.raw_data` ممکن است `cluster` داشته باشد ولی `replay_salt` نداشته باشد. رکورد مچ و اتصال ژورنال حذف نمی‌شوند.

پس از درخواست دانلود یا تحلیل، صف ابتدا آرشیو و Parse موجود را بررسی می‌کند. اگر فایل معتبر و مشخصات کامل Replay وجود نداشته باشند، فقط `cluster`، `replay_salt` و `replay_url` ناقص را پاک می‌کند؛ اطلاعات پایه و ژورنال حفظ می‌شوند. VPS یک GET تازه به `/api/matches/{matchId}` می‌فرستد. اگر cluster و salt معتبر باشند، URL استاندارد Valve ساخته می‌شود و هر سه فیلد پس از تطبیق Match ID یکجا ثبت می‌شوند. اگر دریافت تازه هنوز ناقص باشد، endpoint خصوصی `/v1/metadata/{matchId}` در Worker نیز بررسی می‌شود. این مسیر تنها cluster و salt را برمی‌گرداند و URL معتبر در VPS ساخته می‌شود.

| نتیجه | رفتار صف |
|---|---|
| salt معتبر پیدا شد | تکمیل همان ردیف دیتابیس، سپس دانلود، Parse فقط برای درخواست تحلیل و آپلود آرشیو. |
| OpenDota هنوز salt نداد | `replay_metadata_pending`، تلاش بعدی ۱۰ دقیقه بعد. |
| OpenDota پاسخ ۴۲۹ می‌دهد | مسیر عمومی دیگر و در صورت تنظیم secret، یک درخواست دارای کلید امتحان می‌شود؛ اگر همه محدود باشند، job با فاصلهٔ کنترل‌شده در صف می‌ماند. |
| OpenDota/relay موقتاً در دسترس نیست | job در صف می‌ماند؛ مشکلات metadata هر ۱۰ دقیقه یا بعد از Retry-After بزرگ‌تر بررسی می‌شوند. درخواست‌های تازه تا ۲۰ روز مهلت تلاش دارند. |
| قبلاً در ParsPack ذخیره شده | فایل آرشیو استفاده می‌شود؛ درخواست تازه‌ای به OpenDota یا Valve نمی‌رود. |

رویدادهای `metadata_direct_attempt` و سپس `metadata_direct_ready`،
`metadata_direct_pending` یا `metadata_direct_failed` نتیجهٔ GET مستقیم از VPS را
ثبت می‌کنند. رویداد `metadata_attempt` به مسیر جداگانهٔ Worker/relay تعلق دارد.
در حالت `metadata_direct_failed` کد خطا داخل ستون `detail` ثبت می‌شود؛ کلید API
و URL دارای query در رویدادها ذخیره نمی‌شود. دستور آزمایشی `refreshMatchMetadata`
همین GET مستقیم را اجرا می‌کند، ولی به‌تنهایی job را در دیتابیس تغییر نمی‌دهد.

برای این نسخه استقرار کد VPS و migration `0023` لازم است. تغییر دوبارهٔ Worker یا secret قبلی `REPLAY_PROXY_TOKEN` لازم نیست. کلید OpenDota موجود روی VPS خصوصی می‌ماند. بدون دسترسی یکی از مسیرهای metadata هیچ تضمینی برای به‌دست‌آوردن salt وجود ندارد؛ ۴۲۹ در رویدادهای داخلی ثبت می‌شود و UI وضعیت انتظار Replay را نشان می‌دهد.

کاربران سایت URL یا salt را دستی وارد نمی‌کنند. همان درخواست دانلود یا تحلیل در صف می‌ماند و پس از آماده‌شدن metadata ادامه پیدا می‌کند. Replay کامل و آرشیو فعال قبلی پاک نمی‌شوند.

تست read-only مسیر Worker روی VPS، بدون نوشتن در دیتابیس یا دانلود فایل:

```bash
cd /var/www/dota2notes
sudo -u dota2notes -H node --env-file=/var/www/dota2notes/.env.production \
  apps/web/scripts/replay-parser/probe-metadata.mjs 9023606320 271
```

این probe فقط Worker را می‌سنجد؛ مسیر تازهٔ GET مستقیمِ VPS که پیش از آن در job اجرا می‌شود ممکن است موفق باشد، حتی اگر probe خطای ۴۲۹ بدهد. نتیجهٔ `ok:true` برای همین مچ باید `cluster:271` و `salt:349414436` باشد. وضعیت واقعی با درخواست دانلود یا تحلیل در سایت و سپس لاگ `dota2notes-replay.service` مشخص می‌شود. در `local_replay_jobs` مرحلهٔ `resolving_metadata` و سپس `downloading` دیده می‌شود. هیچ ردیفی را دستی پاک یا ویرایش نکنید.

این تغییر فقط نقص metadata مچ را پوشش می‌دهد؛ اگر OpenDota واقعاً salt را منتشر نکرده باشد، یا فایل دیگر در Valve موجود نباشد، هیچ کدی نمی‌تواند Replay را از Match ID به‌تنهایی بسازد.
