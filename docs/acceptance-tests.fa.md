# تست پذیرش نصب دو VPS و دسکتاپ

این سند سناریوی تست است، نه اعلام موفق بودن آن. برای هر اجرا SHA سورس، نسخه نصاب، زمان، شبکه و نتیجه واقعی ثبت شوند.
تغییر صرف مستندات به تکرار همه این تست ها نیاز ندارد.

## سرور پیش از نصب

| بررسی | نتیجه مورد انتظار |
| --- | --- |
| DNS عمومی API و سایت | `87.107.165.50` در نصب فعلی |
| `GET https://api.dota2notes.ir/health/live` | `200` و service معتبر |
| `GET https://dota2notes.ir/` | `200` |
| route شناخته شده `/api/replays/9059693735/download` از دامنه سایت بدون session | `401`؛ route عمومی باید به Express برسد |
| `/api/admin/service-monitor` بدون session | `401` |
| `/health/ready` از ورودی عمومی | `404` در Nginx |
| همان readiness روی `127.0.0.1:4100` هر میزبان | `200` پس از migration و دسترسی صحیح DB |
| HEAD object انتخابی manifest نصاب | موفق و با طول محتوا |
| SHA Git هر دو VPS | نسخه هدف انتشار |
| سرویس ها | مطابق [جدول نقش ها](environment-and-services.fa.md) |

route دانلود بالا صرفا برای کنترل routing و auth است؛ وجود replay آن مچ قدیمی در Valve فرض نشده است.
health ساده، دسترسی provider یا ایمیل را اثبات نمی کند. مسیر DB ایران و portهای tunnel باید فقط loopback باشند.

## نصب اول و assets

طبق [نصب پاک](desktop-assets-and-install.fa.md) reset را فقط برای همین آزمون انجام بده.

۱. نصب جدید باید قبل از login صفحه assets را نشان بدهد.
۲. اینترنت را حین دریافت قطع و دوباره وصل کن؛ فایل های سالم حفظ و باقی فایل ها دریافت شوند.
۳. اجرای دوم نباید کل فایل های سالم را دوباره بگیرد.
۴. یک فایل رسانه cache را خراب کن؛ بررسی SHA باید آن را ترمیم کند.
۵. uninstall/install عادی بدون reset باید assets سالم را نگه دارد.
۶. فونت و لوگو از اولین صفحه درست باشند؛ تصاویر fa/en و پخش ویدیو در WebView2 واقعی بررسی شوند.

## دریافت خودکار با پنجره بسته

۱. وارد حساب شو، وجود task مستقل و launch option `-gamestateintegration` را بررسی و بازی را restart کن.
۲. پنجره برنامه را کامل ببند؛ Companion باید مستقل بماند.
۳. یک مچ واقعی بازی کن. بعد از ثبت پایان، حداقل پنج دقیقه و زمان لازم provider/صف فرصت بده.
۴. برنامه را باز کن؛ مچ باید بدون Fetch دستی آمده باشد. در شکست، outbox و `match_observations` را جدا بررسی کن.
۵. قطع موقت اینترنت بعد از رویداد نباید رویداد ذخیره شده را حذف کند.
۶. با باز و بسته کردن UI، credential معتبر دستگاه نباید بی دلیل rotate شود.
۷. logout باید فرایند/مجوز محلی را قطع کند؛ بستن پنجره نباید logout تلقی شود.
۸. بازی روی سیستم دیگر باید از طریق reconciliation دوره ای یا Fetch دستی قابل بازیابی باشد.
۹. شروع و پایان نزدیک نیمه شب، روز شروع مچ در تهران و مچ دیررس را بررسی کن.

## Fetch دستی و مصرف درخواست خارجی

یک بازه روزانه/هفتگی/ماهانه را دو بار بگیر. شناسه تکراری نباید ساخته شود و جزئیات کامل مچ های موجود نباید دوباره درخواست شوند.
تعداد `externalRequests` و تعداد مچ جدید ثبت شوند؛ درخواست فهرست برای کشف مچ جا افتاده ممکن است لازم باشد.
بازه بیش از ۲۰ مچ باید بدون خواندن مجدد snapshot از ابتدا ادامه پیدا کند.
خطای provider و quota باید retry محدود یا پیام مشخص بدهند، نه موفقیت ساختگی یا پاک شدن مچ های قبلی.

## اولویت دانلود؛ دو سناریوی مستقل

از replay تازه و قابل دریافت استفاده کن، با اینترنت بدون VPN و بدون انتقال native فعال دیگر.
برای سنجش صف سرور، بهتر است replay در archive از قبل آماده نباشد.

| سناریو | عمل | انتظار |
| --- | --- | --- |
| دانلود یکی از تحلیل ها | پنج مچ تحلیل؛ حین پردازش دانلود یکی از همان پنج مچ | آماده سازی/آرشیو اولویت بگیرد؛ با آماده شدن فایل دانلود شروع شود و منتظر اتمام همه تحلیل ها نماند |
| دانلود خارج از تحلیل ها | پنج مچ دیگر تحلیل؛ دانلود یک مچ خارج از آن پنج تا | تقاضای جدید در صف prepare/archive اولویت محدود بگیرد و در حد ظرفیت آزاد پیش برود |

چهار زمان درخواست، archive ready، شروع native و پایان native ثبت شوند.
انتقال فعال قبلی قطع نمی شود؛ «سریع ترین زمان ممکن» به معنی بدون صف یا زمان صفر نیست.
در مچ ناموجود یا خطای نهایی، task نباید برای همیشه فعال بماند؛ بعد از تلاش مجدد باید درخواست تازه شناخته شود.
تحلیل completed با archive pending به عنوان دانلود آماده نمایش داده نشود.

## مسیر بازی و هماهنگی رابط

- نصب در کتابخانه دوم Steam کشف شود؛ انتقال بازی از داخل Steam باعث کشف دوباره مسیر نامعتبر شود.
- پیش از دانلود، اعتبار مسیر بررسی شود؛ ریپلی موجود نشان «دانلود شده» داشته باشد.
- بین داشبورد، مچ ها و ریپلی جابه جا شو؛ خطای قدیمی نباید وضعیت retry جدید را بازنویسی کند.
- مرحله های سریع با پیشرفت کوتاه و تبدیل عدد به تیک عبور کنند؛ پردازش واقعی برای انیمیشن متوقف نشود.
- تسک کامل از فهرست فعالیت حذف شود؛ خطای نهایی قابل بستن باشد و شمارنده فعال را بالا نگه ندارد.
- شناسه، کپی و دکمه ها در پنل باریک روی هم نیفتند؛ fa/en، scale ویندوز و reduced motion بررسی شوند.

## گزارش نتیجه

موفق، ناموفق و اجرا نشده جدا ثبت شوند. برای شکست، شناسه مچ، مرحله، زمان و کد خطا کافی است؛ env، token و URL امضاشده ارسال نشود.
در هر شکست ابتدا همان لایه بررسی شود؛ نصب fresh سرور یا تغییر DNS قدم پیش فرض نیست.
