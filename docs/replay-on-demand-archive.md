# Replay درخواستی و آرشیو ParsPack

## رفتار جدید

دریافت روزانه/هفتگی فقط summary مچ را می‌گیرد. صف replay در هر tick فقط
درخواست‌هایی را که صریحاً ثبت شده‌اند پردازش می‌کند؛ دیگر از روی ژورنال
مچ جدید کشف نمی‌کند. دکمهٔ تحلیل در Performance، Replay را با parser محلی
پردازش می‌کند. درخواست صرفاً دانلود از مسیر خصوصی
`POST /api/matches/{journalMatchId}/replay` فایل را دریافت و آرشیو می‌کند
و **parser را اجرا نمی‌کند**. این endpoint به صاحب مچ و درخواست با Origin
معتبر محدود است. صفحهٔ `/replays` جست‌وجوی Match ID، درخواست دریافت
و لینک دانلود Replay آرشیوشده را فراهم می‌کند.

برای تحلیل، worker فایل را از آرشیو قبلی یا proxy دریافت می‌کند. اگر قبلاً
تحلیل محلی ذخیره نشده باشد، آن را parse می‌کند.
سپس اگر آرشیو وجود نداشته باشد، فایل را به همان فضای ابری موجود سایت
در ParsPack منتقل و وجود، حجم و SHA-256 آن را بررسی می‌کند. کلید فایل:

```text
replays/YYYY/MM/DD/MATCH_ID.dem.bz2
```

تاریخ، زمان شروع خود مچ به UTC است. کلید فایل‌های قدیمی با
`MATCH_ID_REPLAY_SALT.dem.bz2` در دیتابیس باقی می‌ماند و هنوز خوانده می‌شود.
پیش از استفاده، وجود فایل و حجم/متادیتای آن در پارس‌پک بررسی می‌شود؛ اگر
فایل دستی پاک شده باشد، درخواست تازه از Valve/پروکسی می‌گیرد و دوباره
آرشیو می‌کند. محدودیت ماندگاری Valve همچنان برقرار است.
اگر اول دانلود درخواست شده باشد، درخواست تحلیل بعدی از آرشیو استفاده می‌کند.
پوشهٔ `incoming` فقط برای فایل‌های موقتِ تصادفیِ همین worker است؛ گذاشتن
فایل Replay دستی در آن دیگر ورودی قابل قبول نیست. دستور مستقیم قدیمی
`import-replay.mjs --file` نیز فایل دستی را نمی‌پذیرد. فایل موقت بعد از اتمام
تلاش پاک می‌شود. فایل‌های دستی قدیمی روی VPS خودکار حذف نمی‌شوند و باید
بعد از اطمینان از نیاز نداشتن به آنها، جداگانه توسط اپراتور پاک شوند.
اطلاعات تحلیل ذخیره‌شدهٔ ۹۰ مچ قبلی دست‌نخورده می‌ماند؛
Replayهایشان که در نسخهٔ قدیمی موقت بودند آرشیو نشده‌اند و فقط با درخواست
صریح و دریافت دوباره آرشیو می‌شوند.

## نصب و بررسی در استقرار

پیش از migration `0018_replay_archive`، timer و service Replay را متوقف
کنید و از DB بکاپ بگیرید. این migration
ستون‌های intent و اطلاعات آرشیو را به `local_replay_jobs` اضافه می‌کند.
درخواست‌های ناتمام نسخهٔ قبلی را `failed` می‌کند تا هیچ دانلودی از صف
خودکار گذشته ادامه پیدا نکند؛ رکوردهای `completed` و دیتای تحلیل حذف
نمی‌شوند. همان متغیرهای `CLOUD_SPACE_*` که برای آپلود عکس استفاده می‌شوند
باید در `.env.production` سرویس replay در دسترس باشند. تغییر secret یا
bucket لازم نیست؛ مسیر `replays/` به صورت object key ساخته می‌شود.

سرویس replay همچنان هر دقیقه یک job و هر بار فقط یک فایل را پردازش می‌کند.
برای نمونهٔ کنترل‌شده می‌توان Match موجود و مناسب را با دستور زیر وارد
صف دانلود بدون تحلیل کرد؛ فقط بعد از اطمینان از Match ID صحیح این دستور
را اجرا کنید:

```bash
cd /var/www/dota2notes
sudo -u dota2notes -H node --env-file=.env.production \
  scripts/replay-parser/run-queue.mjs --enqueue MATCH_ID --download-only
sudo systemctl start dota2notes-replay.service
```

برای درخواست دستی تحلیل همان دستور بدون `--download-only` است. مسیر
اصلی کاربران، دکمهٔ Performance و API خصوصی است. برای مشاهدهٔ نتیجه:

```sql
SELECT match_id, status, intent, source, archive_key, archive_bytes, archived_at,
       error_code
FROM local_replay_jobs ORDER BY updated_at DESC LIMIT 10;
```

موفقیت واقعی آپلود به ParsPack باید روی VPS با یک مچ جدید آزمایش شود؛
تست‌های محلی شبکهٔ ParsPack و credentials تولید را ندارند. هنگام خطای
آپلود، job کامل نمی‌شود و فایل خودکار موقت پاک می‌شود؛ تلاش بعدی فایل را
دوباره از منبع می‌گیرد یا، اگر قبلاً آرشیو تأیید شده، از ParsPack می‌خواند.
