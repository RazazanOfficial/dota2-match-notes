# نصب قرارداد تیم و بررسی اولیه در Codex محلی

این بسته فقط دستور پروژه، تعریف عامل و راهنماست. نصاب نرم افزار، تنظیم VPS، dependency، مدل و حساب کاربری را تغییر نمی دهد.
فایل های انگلیسی برای قرارداد فنی یکدست نوشته شده اند؛ گفتگو و توضیح برای MeriJ فارسی باقی می ماند. این انتخاب ادعای برتری ذاتی زبان انگلیسی نیست.

## قبل از کپی

پوشه فعلی ریپو را در Codex محلی باز کن؛ در سیستم شناخته شده مسیر `D:\Projects\dota2-match-notes` بوده است، اما مسیر واقعی را بررسی کن.
در این مرحله فقط یک checkout و یک جریان ویرایش فعال کافی است. نیازی به clone دوباره یا ده چت برای نقش ها نیست.

اگر `AGENTS.md` یا یکی از نام های `.codex/agents/` از قبل وجود دارد، ابتدا اختلاف را بخوان و محتوای مفید موجود را ادغام کن؛ آن را کورکورانه overwrite نکن.
Global و nested `AGENTS.override.md` نیز ممکن است موثر باشند؛ بدون بررسی آنها را حذف نکن.
این بسته `.codex/config.toml` ندارد تا مدل، MCP، trust و مجوزهای فعلی حفظ شوند.

## فایل ها با مسیر نسبی ریپو

| مسیر | کاربرد |
| --- | --- |
| `AGENTS.md` | قواعد اصلی و جدول ۱۱ نقش |
| `.codex/agents/*.toml` | یازده تعریف عامل با name، description و developer_instructions |
| `.agent-work/.gitignore` | قانون ثبت شده برای نادیده گرفتن محتوای موقت تسک ها |
| `docs/codex/team-workflow.fa.md` | قرارداد همکاری و مسیریابی |
| `docs/codex/task-template.md` | قالب اختیاری یک تسک مهم |
| `docs/codex/research-and-validation.fa.md` | مبنای تحقیق، تصمیم ها و محدودیت بررسی |
| همین سند | راه اندازی و بررسی محیط واقعی |

فایل ها UTF-8/LF هستند. نام درست فایل `AGENTS.md` است، نه `aigent.md`.
پس از کپی/ادغام، یک چت تازه در پروژه باز کن تا دستورها از شروع نشست بارگذاری شوند.
نصب این بسته به معنی commit، push، merge، اتصال Figma محلی یا فعال شدن دسترسی VPS نیست.

## محل فایل های موقت و تست

Codex برای اسکریپت یک بار مصرف، خروجی تست، trace و داده ساختگی موقت از `.agent-work/<task-id>/` استفاده می کند.
فایل `.agent-work/.gitignore` همراه بسته است و محتوای موقت را نادیده می گیرد؛ فقط خود این فایل قانون در Git ثبت می شود تا روی سیستم بعدی هم برقرار باشد.
فایل `.gitignore` ریشه جایگزین نمی شود. اگر همین پوشه یا قانون از قبل وجود داشت، محتوای آن حفظ و ادغام شود.
تست رگرسیون ماندگار در پوشه تست فعلی پروژه و تصمیم های لازم در docs ثبت می شوند؛ جای آنها پوشه موقت نیست.
داده واقعی دیتابیس، token و لینک امضا شده در این پوشه هم قرار نمی گیرند. ignore مجوز نگهداری secrets نیست.

پس از کپی، این بررسی فقط خواندنی را در PowerShell داخل ریپو اجرا کن؛ نیازی به ساخت فایل نمونه نیست:

```powershell
git check-ignore --no-index -- .agent-work/setup-check/probe.txt
if ($LASTEXITCODE -ne 0) { throw "Temporary folder is not ignored; stop and inspect ignore rules." }

git check-ignore --no-index -- .agent-work/.gitignore
if ($LASTEXITCODE -eq 0) { throw "The scratch ignore policy is itself ignored; inspect existing rules." }
if ($LASTEXITCODE -ne 1) { throw "Git ignore check failed." }
```

فرمان اول باید مسیر `probe.txt` را نشان دهد. فرمان دوم باید بدون خروجی باشد و exit code برابر ۱ بدهد.
Codex فقط فایل های موقت تسک خودش را پاک می کند؛ پاک کردن همه پوشه یا فایل های تسک های دیگر روال عادی نیست.

## بررسی اول: فقط شناخت و کشف دستورها

در چت تازه این درخواست را مطرح کن: فقط بررسی کن؛ هیچ فایل، وضعیت Git، حساب یا سروری را تغییر نده. مسیر پروژه، branch/HEAD، دستورهای موثر و نام عامل های واقعا قابل فراخوانی را گزارش کن. سپس نقش ها و مرز مجوزها را خلاصه کن.

انتظار داریم:

- مسیر و نسخه واقعی گزارش شود؛ نام و وضعیت از حافظه چت قبلی گرفته نشود.
- فایل root و overrideهای موثر شناسایی شوند.
- ۱۱ نام lead، task_analyst، qa، backend، database، frontend، ux، release، security، performance و docs قابل کشف باشند.
- ادعای دسترسی به ابزار، Figma یا VPS بدون بررسی نشود.
- اگر نسخه نصب شده schema فعلی custom agent را نمی شناسد، اختلاف نسخه گزارش شود؛ هیچ کلید حدسی به config اضافه نشود.

در CLI نصب شده می توان از `codex --version` برای ثبت نسخه استفاده کرد. این فایل حداقل نسخه ادعایی برای هر قابلیت تعیین نمی کند؛ رفتار نسخه واقعی بررسی شود.

## بررسی دوم: یک واگذاری واقعی و فقط خواندنی

از هماهنگ کننده بخواه با عامل `database` فقط محل schema و روش migration و مجوز compute را بررسی کند و نتیجه را بدون تغییر برگرداند.
باید فعالیت یک عامل واقعی و گزارش دارای مسیر سورس ببینی؛ صرف نوشتن `[database]` در پاسخ کافی نیست.
بعد diff را بررسی کن؛ product code، config و Git state نباید تغییر کرده باشند.
اگر ابزار واگذاری در دسترس نیست، محدودیت ثبت شود و بازبین مستقل اجراشده فرض نشود.

## بررسی سوم: هویت Git، بدون انتشار

از عامل بخواه موثر بودن تنظیم author/committer و حساب احراز هویت شده GitHub را بدون نمایش credential بررسی کند.
در صورت نداشتن ایمیل تایید شده، از MeriJ همان یک اطلاعات لازم پرسیده شود؛ نام/ایمیل از حساب Figma یا نمونه این بسته حدس زده نشود.
این مرحله نباید commit تست، push، collaborator یا تغییر global config بسازد.
در اولین commit واقعی مجاز، metadata و پیام نهایی قبل از push بررسی شوند؛ هیچ Co-authored-by مربوط به AI اضافه نباشد.
اگر کلاینت انتساب را خودکار اضافه می کند، سازوکار همان نسخه باید بررسی شود؛ این بسته کلید تنظیم ناشناخته برای آن نمی سازد.

## بررسی چهارم: ادامه پس از تغییر کد

پس از یک تسک آزمایشی غیرحساس و مورد توافق، کار را در چت دیگر ادامه بده.
از چت قدیمی بخواه قبل از هر اصلاح، نسخه و diff و فایل مرتبط را دوباره بخواند.
انتظار: کد امروز مبنا باشد؛ برنامه قدیمی یا branch قبلی خودکار جای آن قرار نگیرد. این آزمون بدون تغییر آزمایشی واقعی فقط سناریوی پیشنهادی است.

## Figma و دسترسی ها

اتصال Figma این گفتگو موفق بوده است؛ قابل استفاده بودن همان ابزار در Codex محلی باید جدا با یک فایل/frame مشخص و خواندنی تایید شود.
ساختن فایل تازه یا تغییر طرح، درخواست طراحی جدا می خواهد. برای تایید اتصال، طرح آزمایشی بی هدف ایجاد نکن.
مجوز اصلی نشست را حفظ کن؛ تعریف متخصص در TOML محدودیت واقعی سیستم عامل ایجاد نمی کند.

## شروع اولین تسک محصول

بعد از موفقیت بررسی های لازم، نیاز واقعی را به زبان معمولی در یک چت اصلی بگو.
کاربر لازم نیست نام همه نقش ها یا پرامپت انگلیسی آماده بدهد. هماهنگ کننده باید ابهام فنی را بررسی، تسک را روشن و فقط متخصص های مرتبط را استفاده کند.
برای انتشار و استقرار، نسخه و هدف مجاز باید مشخص باشند؛ نتیجه live هر میزبان جدا گزارش شود.
