# قرارداد کار تیم MeriJ و Codex

این راهنما قرارداد پروژه است؛ تضمین مهارت انسانی، استقلال کامل بازبین ها یا درصد بهبود نیست.
[AGENTS.md](../../AGENTS.md) قواعد مشترک را بارگذاری می کند. تعریف متخصص ها در `.codex/agents/` است؛ این راهنما جزئیات کار را هنگام نیاز توضیح می دهد.

## اختیار و مسئولیت

MeriJ مالک محصول است: نیاز کاربر، اولویت، هزینه، پذیرش محدودیت و تصمیم انتشار را تعیین می کند.
هماهنگ کننده اصلی مسئول شناخت سورس، نقد روش پیشنهادی، پیشنهاد فنی، تقسیم کار و بررسی خروجی هاست.
متخصص باید یافته و شاهد بدهد؛ عنوان سنیور، توافق چند عامل یا تعداد ترمینال نشانه صحت نیست.
امنیت، پرفورمنس و کیفیت پایه مسئولیت همه نقش ها هستند. بازبین تخصصی هنگام تغییر مرتبط وارد می شود.

اولویت جدول ترتیب اجباری ورود در هر تسک نیست. در بازطراحی، UX زودتر از فرانت وارد می شود؛ در تغییر auth، امنیت از ابتدا مطرح است.

## برچسب در متن چه می کند؟

`[database]` یک نام قراردادی است. عامل واقعی نام `database` دارد و فایل تعریفش `database.toml` است.
هماهنگ کننده باید درخواست را به ابزار واگذاری واقعی بدهد و نتیجه آن را جمع کند؛ نوشتن چند عنوان نقش در پاسخ، اجرای چند متخصص نیست.
کاربر لازم نیست همه نقش ها را نام ببرد. توضیح عادی مثل «این رابطه ها را بررسی کن» هم باید به تشخیص حوزه مناسب منجر شود.
اگر ابزار واگذاری یا تعریف عامل در محیط موجود نیست، این موضوع گفته می شود و بررسی در همان زمینه انجام می شود؛ بازبینی مستقل ادعا نمی شود.

## روند متناسب با اندازه تسک

### تغییر کوچک و روشن

فایل مرتبط و diff فعلی خوانده می شود؛ تغییر محدود، بررسی مناسب و گزارش انجام می شود.
برای اصلاح متن، همه تست ها، جلسه معماری و فایل تسک تازه الزامی نیست.

### قابلیت یا تغییر مهم

۱. **شناخت:** رفتار فعلی، مسیر کد و نیاز واقعی کاربر.
۲. **تعریف:** مسئله، محدوده، معیار پذیرش و ابهام اثرگذار.
۳. **تصمیم:** گزینه های معقول و پیشنهاد با هزینه/ریسک؛ توافق پیش از تغییر مهم.
۴. **اجرا:** تغییر در محدوده توافق شده، با مالکیت روشن فایل ها.
۵. **بررسی:** تست و بررسی diff نهایی؛ بازبین جدا برای ریسک مهم.
۶. **تحویل آماده انتشار:** نتیجه، شواهد، موارد اجرا نشده و برنامه انتشار.
۷. **انتشار و پذیرش:** فقط در صورت درخواست/مجوز همان عملیات، با نسخه و محیط مشخص.

«آماده انتشار» با «مستقر و تایید شده» متفاوت است. بعد از توافق، اجرای کارهای معمول و تست های مرتبط به تایید دوباره هر فایل نیاز ندارد.
اگر تصمیم تازه ای هزینه، معماری یا تجربه کاربر را عوض می کند، همان تصمیم روشن شود؛ کارهای مستقل نباید بی دلیل معطل بمانند.

## رفتار انتقادی

ابتدا هدف را از راه حل خام جدا کن. ایراد باید با اثر، شاهد و جایگزین بیان شود.
اگر کاربر بگوید «همه درخواست ها را موازی کنیم»، باید quota، ترتیب، ظرفیت و اندازه گیری بررسی شوند.
اگر بگوید «همه پکیج ها latest باشند»، سازگاری و ریسک ارتقا بررسی شود.
اختلاف ترجیح بصری با باگ فنی یکی نیست؛ مخالفت نمایشی هم ارزش ندارد. بعد از روشن شدن tradeoff، انتخاب آگاهانه کاربر ثبت و دنبال شود.
از عبارت هایی مثل «قطعا مشکل از شبکه است» بدون شواهد تفکیک کننده استفاده نشود.

## بسته واگذاری به متخصص

برای واگذاری واقعی، هماهنگ کننده این اطلاعات را منتقل کند:

- شناسه/عنوان تسک و نتیجه مورد انتظار؛ منبع تصمیم ها و معیار پذیرش.
- مسیر واقعی checkout، branch/HEAD و تغییرهای مرتبط که هنوز commit نشده اند.
- حالت کار: بررسی، پیشنهاد یا پیاده سازی؛ مسیرهای تحت مالکیت و فایل های خارج محدوده.
- قراردادهای لازم و فرضیات حل نشده؛ بدون env، token یا خروجی حجیم نامربوط.
- فرمان ها و منابع مجاز، fixture/DB/پورت و محدودیت همزمانی.
- خروجی مورد انتظار: یافته با مسیر و شدت، تغییرات، تست، محدودیت و مانع.

فقط read/review مستقل را پیش فرض موازی کن. در پیاده سازی همزمان یک فایل دو نویسنده نداشته باشد؛ branch/index، dependency install، build output و fixture مشترک نیز مالکیت می خواهند.
متخصص ها خودشان زنجیره دیگری از عامل ها نمی سازند. ادغام و تغییر وضعیت Git با هماهنگ کننده است.

## چت جدید، ادامه چت قدیمی و worktree

برای شروع، یک checkout محلی و یک جریان ویرایش فعال کافی است. چت تازه برای تسک تازه پیشنهاد نظم است، نه الزام برای هر پیام.
بعد از اتمام تسک و ادغام، بهبود بعدی همان قابلیت می تواند تسک تازه بر مبنای main فعلی باشد.
در ادامه چت قدیمی، branch/commit/diff و فایل های مرتبط دوباره خوانده می شوند؛ هیچ کد قدیمی از حافظه روی فایل جدید نوشته نمی شود.
اگر worktree جدا وجود دارد، ادغام main فایل های آن را خودکار تازه نمی کند؛ هماهنگ کننده ابتدا وضعیت و روش ادغام را مشخص می کند.
فایل های نادیده گرفته شده مانند env خودکار بین همه محیط ها مشترک فرض نمی شوند. به محیط تست، secrets تولید کپی نشود.

برای تسک بلند، یک پرونده کوتاه با قرارداد و پیشرفت نگهداری کن. [قالب اختیاری](task-template.md) نقطه شروع است؛ اگر ریپو همین مفهوم را دارد همان را ادامه بده.
فایل پرونده حاوی شواهد و تصمیم است، نه transcript کامل گفتگو و نه نسخه دیگری از runbook.

## فایل های موقت و ماندگار

مسیر موقت هر تسک `.agent-work/<task-id>/` است: اسکریپت یک بار مصرف، خروجی تست، trace و fixture موقت آنجا قرار می گیرند.
قانون `.agent-work/.gitignore` در Git نگهداری می شود اما محتوا نادیده گرفته می شود؛ عامل قبل از نوشتن موثر بودن آن را بررسی می کند.
تست رگرسیون بخشی از محصول است و در مسیر تست فعلی پروژه ثبت می شود. تصمیم لازم برای ادامه کار نیز در docs می ماند.
نادیده گرفتن فایل، حفاظت امنیتی نیست؛ secrets و dump واقعی آنجا ذخیره نشوند. پاکسازی به فایل های همان تسک محدود است.
`.codex/` محل تعریف عامل هاست و برای خروجی موقت استفاده نمی شود.

## بررسی و ادغام

بازبین diff نهایی و معیار پذیرش را بررسی می کند، نه فقط گزارش نویسنده را.
یک یافته باید محل، شدت، سناریوی شکست و شاهد داشته باشد. تعداد یافته ها معیار کیفیت نیست.
اصلاح نویسنده، یافته را خودکار بسته نمی کند؛ بررسی دوباره قسمت متاثر لازم است.
در دسترس نبودن Windows، provider یا بازبین مستقل باید روشن گزارش شود؛ pass ساختگی نداریم.
شکست مستقل موجود در baseline مانع ادعای «همه سبز» است؛ بدون اجازه به تغییر بی ربط تبدیل نشود.

## Git با حساب خود MeriJ

هویت author/committer با حساب احراز هویت شده برای push دو موضوع جدا هستند؛ هر دو باید تایید شوند.
ایمیل واقعی از تنظیم تایید شده گرفته شود؛ ایمیل این گفتگو یا حساب Figma، ایمیل Git فرض نشود.
commit های تازه نباید trailer یا انتساب Codex/AI داشته باشند و هیچ collaborator جدیدی اضافه نمی شود.
نام شاخه طبق الگوی مخزن مانند `fix/replay-transport` یا `feat/automatic-library` باشد؛ پیشوند `codex/` استفاده نشود.
پیام commit از الگوی `fix: ...` یا `feat: ...` پیروی می کند؛ `:` و فاصله در نام شاخه معتبر نیستند.
نام شاخه به خودی خود author یا committer را تعیین نمی کند.
اگر خود برنامه یا ابزار انتسابی را خودکار اضافه می کند، پیش از push تشخیص و تنظیم سازگار آن بررسی شود؛ صرف دستور این فایل تضمین حذف آن نیست.
تاریخچه دیگران برای تغییر نام نویسنده بازنویسی نمی شود. تنظیم global یا کلیدهای کاربر بی دلیل عوض نمی شوند.

طبق تصمیم فعلی MeriJ، commit، push و merge را خود او انجام می دهد؛ عامل این عملیات را اجرا نمی کند.
عامل تغییرات و بررسی ها را کامل و دستورهای لازم را تحویل می دهد؛ انتشار روی Git و اجرای استقرار روی VPS با MeriJ است.

## ابزار و دسترسی

Figma و ابزار تصویر در تسک مرتبط استفاده می شوند؛ متصل بودن حساب مجوز ایجاد یا تغییر هر فایل نیست.
قابلیت خواندن طراحی با مجوز نوشتن آن جدا بررسی شود. برای UI فعلی، component و design token موجود دوباره ساخته نشوند.
Playwright ظاهر/رفتار browser را بررسی می کند؛ Tauri، نصب، Steam و GSI به شواهد Windows واقعی نیاز دارند.
پیکربندی مدل، permissions، MCP و حساب ها در این بسته overwrite نمی شود. حالت فقط خواندن یک بازبین در متن دستور، sandbox فقط خواندن ایجاد نمی کند.

## سنجش روش همکاری

در چند تسک نماینده، زمان تا پذیرش، دوباره کاری و ایراد بعد از تحویل ثبت شوند؛ هزینه و زمان بازبینی هم حساب شوند.
نتایج با نسخه، scope و شرایط اجرا همراه باشند. مقایسه تسک های متفاوت تخمین عملی است و اثبات علت یا درصد عمومی بهبود نیست.
عامل بیشتر فقط وقتی اضافه شود که کار مستقل یا بازبینی جدا ارزش واقعی ایجاد کند.
